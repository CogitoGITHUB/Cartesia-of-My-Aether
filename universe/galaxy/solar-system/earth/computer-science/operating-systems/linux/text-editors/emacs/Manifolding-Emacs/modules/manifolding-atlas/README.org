* The idea

Atlas treats knowledge as something that can be manifolded — folded, inverted, stretched, and re-projected without ever becoming sacred.
"Manifolding" is not a metaphor.
It describes the actual mechanism: recursive transformation of representations.

A note is not merely a document.  
An unfolding is not merely metadata.  
A schema is not merely validation.  
A prompt is not merely a question.  
A link is not merely navigation.

Together they form a structure that can be queried, transformed, validated, connected, expanded, compressed, and rebuilt while the underlying files continue their slow, inevitable decay.

The fundamental rule is simple and merciless:

#+begin_quote
Files preserve material.
Schemas describe possible structure.
Machinery transforms structure.
Interfaces expose transformations.
Indexes accelerate navigation.
Feedback exposes decomposition.
The next representation is allowed to replace the previous one.
#+end_quote

If the database disappears, the knowledge survives (for now).  
If the configuration disappears, the Org files survive (for a while).  
If the schemas change, the knowledge can be reinterpreted until the next reinterpretation becomes necessary.

* PostgreSQL substrate

The disposable index outgrew its file. SQLite remains the frozen
reference, but the live substrate is PostgreSQL on Termux — same
emacsql DSL, same tables, same extractors, new wire. The migration
changes where derived state lives, never what the truth is: the
vault rebuilds everything from org files, which is why cutover is a
fresh rescan rather than row surgery.

** Termux provisioning (shell, one time)

: pkg install postgresql
: mkdir -p $PREFIX/var/lib/postgresql
: initdb $PREFIX/var/lib/postgresql

Authentication is local trust for now — auto-login, no password
(the =initdb --auth=trust= default; all local/host pg_hba lines read
=trust=). This is a deliberate shortcut for the building phase, not
the end state: the code already reads the password from auth-source
when one exists, so switching later means creating the SCRAM
password, flipping pg_hba to =scram-sha-256=, adding the =~/.authinfo=
line below, and restarting — no code changes. A =test= password was
considered and not used; trust made it unnecessary. Then:

: pg_ctl -D $PREFIX/var/lib/postgresql start
: createuser -s atlas
: createdb -O atlas atlas

When the SCRAM stage comes, the password lives in =~/.authinfo= and
nowhere else — never a defcustom, never source, never the repo:

: machine localhost port 5432 login atlas password <secret>

No filesystem encryption is attempted here; the local Termux
environment is the security boundary. At-rest protection is a
separate future project, not part of this migration.

** Daily operation

: pg_ctl -D $PREFIX/var/lib/postgresql start
: pg_ctl -D $PREFIX/var/lib/postgresql stop

Postgres is started by hand, on purpose. Emacs never starts it;
instead =(my/manifolding-atlas-db-health)= reports one of five
states with the exact recovery step: CONNECTED, DOWN (start it),
AUTH-FAILED (authinfo + pg_hba — unreachable while trust is on),
DATABASE-MISSING (createdb), SCHEMA-OUTDATED (rescan). Backup changes meaning with the move:
the vault no longer contains its own index, so back up both — files
as before, plus =pg_dump atlas= on whatever rhythm the vault
deserves.

** Cutover checklist

1. Provision + auth per above; confirm =psql atlas= connects.
2. In Emacs: =(setq my/manifolding-atlas-db-backend 'pg)=, reconnect.
3. Health must read CONNECTED (an empty database reports
   SCHEMA-OUTDATED until the first rescan builds tables — expected).
4. Full vault rescan. Extractors rebuild notes, links, mm_nodes,
   mastering_schedule, citations, rules, dictionary from org files.
5. Semantic validation against the frozen SQLite reference — not
   row counts but meaning: note/link counts, IDs, paths, titles,
   tags/unfoldings, link relationships, mm topology
   (roots/children/order), mastering rows, representative queries
   including graph traversal (=descendants= / =component= /
   =shortest-path= agreement is the strongest proof the substrate
   moved cleanly), then restart/reconnect plus several real sessions.
6. Rollback at any point before step 5 signs off: set the backend
   back to =sqlite=; the file and its code path are untouched.
7. Decommission (later, explicit): delete the SQLite branch and the
   frozen =.db= file. One substrate.

* The unfolding picker

Every prompt is a interactive editor, not a question.

| Key     | Action                                                        |
|---------+---------------------------------------------------------------|
| m       | apply the option under cursor — again removes it from the note |
| l       | make it unfolding: create the unfolding-note and edit its content         |
| a       | key-selection-jump straight to any option line             |
| RET     | next prompt — refused until something was applied              |
| q       | skip this prompt (first-option default)                        |
| b / B   | step back one · revisit any answered prompt                    |
| Q / C-g | abort everything — the draft note is deleted                   |

Nothing commits until you mark it.  
A mistaken mark is un-applied with the same key.  
Going back never repeats what you already answered.  
Aborting deletes the draft so nothing half-made survives.

Multi-choice prompts accumulate marks; clearing them all removes the
unfolding.  Reopened prompts restore their applied value, highlighted
in bold, so changes are always visible before they become real.

Session pickers open with a key-selection loop already armed: typing
letters of an option jumps there and applies it immediately; pausing surfaces
the key hints instead.

* Validation

Validation does not interrupt thought.  
There are no surprise minibuffers announcing that your note has committed some terrible epistemological crime.

Validation happens at index time.
Violations and lifecycle events accumulate in the admin queues:

: admin/Static Blueprints            static defaults wanting unfolding links
: admin/Broken Unfoldings          broken links rooted in a drawer unfolding
: admin/Missing Links              broken id: links between notes
: admin/ReManifold                 deleted files (with orphaned unfoldings)
: admin/Added Heading Blueprints   per-file log of swept-in drawer keys
: admin/Deleted Heading Blueprints per-file log of swept-out drawer keys

Every note holding static defaults becomes a TODO carrying:

: :SCHEMAS:
: :VIOLATIONS:

Static means: the value is missing or still a plain default
(~TODO~ and friends) instead of a live ~[[id:…][label]]~ unfolding
link. Open the entry with RET, answer the prompt — or press ~l~ in
the picker to make the value a live unfolding note. Link-structure
breaks (~wrong-type~, ~invalid-reference~) never land here; those
stay visible via flymake and the doctor.

and every swept drawer key becomes a TODO carrying:

: :BLUEPRINT_KEY:
: :NOTE_FILE:
: :DEFAULT_VALUE:

Then:

: SPC v E

runs the reinforcement sweep.

And:

: SPC v f

walks through the violations.

RET on an ~Added Heading Blueprints~ entry opens the note in an
org-capture buffer positioned on the added ~:KEY:~ line
(~file:PATH::*KEY~ search anchor + capture advice); the admin TODO
stays open until marked DONE manually. Deleted-queue entries keep a
plain file open — the line is gone, there is nothing to anchor to.

The philosophy is simple and slightly sadistic:

#+begin_quote
Capture first.  
Repair structure deliberately.  
Never let validation become friction.  
Let the holes remain visible long enough to hurt.
#+end_quote

Flymake provides the immediate editing feedback.
The reinforcement system provides the global feedback.

* Added/Deleted Heading Blueprints

Adding or deleting a blueprint file is a vault event, detected by
boot state-comparison (not hooks), so it works however the file
changed. The sweep writes one TODO per affected note:

- added → ~admin/Added Heading Blueprints~, heading
  ~Added property KEY to [[file:PATH::*KEY][title]]~ with
  ~:BLUEPRINT_KEY: :NOTE_FILE: :NOTE_ID: :DEFAULT_VALUE:~
- removed → ~admin/Deleted Heading Blueprints~, heading

* Manifold

The manifold domain is where spatial transformation becomes concrete.
A note stops being merely a document and becomes a structural object that can be placed, moved, and re-projected in relation to other objects.

A note can be placed as:

: root
: parent
: child
: sibling

The structure becomes navigable in three dimensions.  
The knowledge graph becomes a volume that can be reshaped without rewriting the underlying knowledge.  
You are no longer scrolling a buffer.  
You are moving through a temporary architecture of identities.

Traversal is a first-class keyboard state ([MAP], entered via =SPC m
t= over any note): =s/n= walk the depth axis (parent up, child down,
headings ascending to their file card first), =h/t= step the sibling
axis (previous/next, stopping dead at both ends — never wrapping),
=r= root, =g= group card, =m= full map, =P/A= placement, =B= crosses
into mastering by reviewing the branch at point, =q= back to org.
The map shows =[stage]= on every line plus branch coverage
(=x/y= cards at UNDERSTANDING or above) in the group buffer, and
=manifold-map.json= carries stage alongside status and topology as
the future graphical renderer's contract — a projection, never a
source of truth.

Ownership law (binding on both subsystems and the future renderer):
mind-map owns topology, order, relationships, roots, headings,
location, display, and traversal; mastering owns stage, review, due,
schedule, session, queue, grade, attestation, and progression; STATUS
plus the suspend flag are shared. Reading another subsystem's data —
displaying it, filtering by it, traversing it, querying it — never
constitutes ownership. Ownership means authority for mutation and
semantics. Neither subsystem may infer ownership from consumption.

* Mastering

Mastering introduces temporal transformation.
It turns notes into a memory system with a half-life — and a spine
that says how far each card has traveled from ignorance to original
contribution.

Every note is born enrolled: STAGE=AWARE, STATUS=ACTIVE. The spine
runs UNSEEN → AWARE → ACQUIRING → UNDERSTANDING → CAPABLE →
PROFICIENT → EXPERT → ADAPTIVE → GENERATIVE → CONTRIBUTING, and the
stage token is the note's first tag. Reviews measure memory only, so
the review loop advances just two gates on its own (first contact →
AWARE, first success → ACQUIRING); everything above ACQUIRING is
claimed through attestation with recorded evidence, never inferred.
STATUS (ACTIVE/SUSPENDED/ARCHIVED/DORMANT) is orthogonal — suspending
a note freezes practice without demoting knowledge.

The Atlas tracks:

: STAGE / STATUS / MASTERING_* (schedule) / STAGE_EVIDENCE / LAST_VALIDATED

and builds:

- due queues (ACTIVE, seen stages only; UNSEEN triaged separately;
  ordered parents-before-children along the map — foundations first)
- overdue queues
- branch-scoped sessions (=SPC v d= reviews the branch at point)
- review sessions (graded n/f, attest with evidence, suspend inline)
- participation via status flips (no exits, only pauses)
- review scheduling (SM-2 variant: proto intervals, synolon scaling,
  amnesia failures, anagnosis streaks, lethe resets, interval fuzz)

Knowledge therefore has a temporal dimension.
A note can exist.
A note can be connected.
A note can be reviewed.
A note can climb — each rung gated by evidence, not by optimism.
And then the mastery itself will eventually be declared insufficient.

* The real model

Atlas looks like a note system from the outside.
That description is too small and already decaying.

It is closer to a small knowledge operating system:

- Org is the filesystem
- SQLite is the index
- Schemas are the type system
- Prompts are the interface compiler
- Domains are applications
- Templates are generators
- Wormhole is composition
- Validation is the type checker
- Mastering is the memory scheduler
- Routines are the execution layer
- The UI is the viewport
- The loader is the coordination layer that holds the decomposition at bay

The conceptual invariants:

1. The files are the durable substrate.
2. The database is a disposable representation/index.
3. Schemas are executable knowledge structures.
4. Prompts are generated interfaces to those structures.
5. Domains are transformations operating over the common substrate.
6. Templates are structural generators.
7. Validation observes discrepancies between structures and their declared forms.
8. Mastering introduces temporal transformation of knowledge.
9. Manifold introduces spatial/structural transformation.
10. The UI is a viewport into the current representation, not the authority.
11. The configuration itself is subject to transformation.
12. No current representation is sacred.
13. The durable invariant is not preservation of a particular map; it is preservation of the ability to produce new maps from surviving material.

#+begin_quote
Everything is allowed to change.
Nothing is allowed to become unnecessarily permanent.
#+end_quote

That is why the system is called Manifolding Atlas.
It does not merely store a map of knowledge.
It is a system for continuously producing and reshaping maps from surviving knowledge.

The distinction that matters:

The map is not the knowledge.
The map is not even the final product.
The map is an intermediate representation.

Manifolding is the machinery that allows representations
to be produced, inspected, folded, unfolded, transformed,
replaced, and projected again from surviving material.

Reshape the schema.
Reshape the prompts.
Reshape the relationships.
Reshape the domains.
Reshape the representation.
Reshape the map.

The files remain.
The structure evolves.
The evolution is temporary.
The machinery that produces the next evolution is the enduring idea.

** 1. WHAT THIS SYSTEM IS

Manifolding Atlas is a local-first org-based knowledge/task system inside Emacs. Everything is a *note* (an org file = file-note, or an org heading with =:ID:= = heading-note). Notes carry structured metadata in *property drawers* called *unfoldings* (=:KEY: value=). Some unfoldings are *live-properties*: instead of plain text they render the live content of another note inline via *wormholes* (=#+wormhole: [[id:UUID][LABEL]] :property= transclusion from the vendored =atlas-wormholes= engine — overlays that sync edits both ways). All notes/links/tags/aliases are indexed into SQLite =manifolding-atlas-db= (emacsql, =admin/manifolding-atlas.db=) so find/search/backlinks/rules/mastering/routines query the DB instead of re-parsing org. A *blueprint* system (org files defining reusable unfolding schemas + pick-lists) drives prompting: RET on a property asks which value, file creation asks which body template. A modal *keyboard/hydra* system (=SPC= leader) exposes all of it.

** 4. BLUEPRINT SYSTEM (current unified tag-based format)

#+begin_example

:ID: <slug>

** OPTION1
